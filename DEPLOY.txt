====================================================================
部署說明：線上端 (Docker) 與本機門市端 (Windows)
====================================================================

架構
- 本機門市端：Windows 電腦 + Waitress (serve_windows.py) + SQLite (database/menu.db)，可完全離線營業。
- 線上端 (SYNC_ROLE=hub)：Linux 主機 + Docker：
    caddy (自動 HTTPS 反向代理，80/443) → app (gunicorn gthread，多 worker) → postgres + redis
  相關檔案：Dockerfile、docker-compose.yml、deploy/hub.env.example、deploy/gunicorn.conf.py、
            deploy/entrypoint.sh、deploy/Caddyfile。


一、線上端部署 (Docker)
--------------------------------------------------------------------
1. 準備
   - Linux 主機，已安裝 Docker Engine 與 docker compose 外掛 (docker compose version 可執行)。
   - 網域的 DNS A/AAAA 記錄指向這台主機；防火牆開放 80、443 (TCP) 與 443 (UDP，HTTP/3)。
     Caddy 第一次啟動時會自動向 Let's Encrypt 申請憑證，80 埠必須能從外部連入。
   - 主機時區不影響容器：容器內固定 TZ=Asia/Taipei (程式以台灣時間計算營業日)。

2. 設定
     cp deploy/hub.env.example .env.hub
     chmod 600 .env.hub
   編輯 .env.hub：
   - SITE_DOMAIN：網域，例如 kiosk.example.com
   - POSTGRES_PASSWORD 與 DATABASE_URL 中的密碼 (兩處要相同；請只用英數字)：
       openssl rand -hex 24
   - SECRET_KEY (必填，未設定時 app 容器會拒絕啟動)：
       openssl rand -hex 32
     多個 worker 共用這把金鑰；設定後不要再改 (改了所有人要重新登入)。
   - ADMIN_USERNAME / ADMIN_PASSWORD：預設店家負責人 (平台管理者) 的帳密，只在第一次建立帳號時使用。
   以下已由 docker-compose.yml 固定，不需設定：REDIS_URL、AUTO_MIGRATE=0、TRUSTED_PROXY_COUNT=1、
   SESSION_COOKIE_SECURE=1、SYNC_ROLE=hub、上傳檔路徑。

3. 啟動
     docker compose up -d --build
     docker compose ps                  (app、postgres、redis 顯示 healthy 即完成)
     curl https://您的網域/healthz       (應回 {"database":"ok","status":"ok"})
   app 容器啟動時會先執行 flask --app run setup (升級資料庫結構 + 建立預設資料)，再啟動 gunicorn；
   資料庫遷移只在這一步執行一次，gunicorn 的 worker 不會各自遷移。

4. 第一次登入
   - 開啟 https://您的網域/admin，以 .env.hub 的 ADMIN_USERNAME / ADMIN_PASSWORD 登入。
   - 若 .env.hub 沒有設定帳密，系統會產生一組隨機帳密並只在第一次啟動時寫入 log：
       docker compose logs app | grep 預設負責人
     請立即登入並記錄到安全的地方。
   - 忘記密碼：.env.hub 設定 ADMIN_PASSWORD 與 RESET_ADMIN_PASSWORD_ON_START=1，
     執行 docker compose up -d 重啟 app 一次，登入後改回 0 再 docker compose up -d。
   - 員工帳號在後台「員工帳號」(/admin/staff) 建立。

5. 查看 log
     docker compose logs -f app         (gunicorn 存取記錄與程式訊息)
     docker compose logs -f caddy       (HTTPS 憑證申請、反向代理)
     docker compose logs --since 1h postgres
   每個服務的 log 會自動輪替 (每檔 20MB、保留 5 檔)。
   存取記錄第一欄是顧客真實 IP (X-Forwarded-For)，第二欄是 Caddy 的容器位址。

6. 資料保存位置 (docker volume，docker compose down 不會刪除；down -v 才會刪除，請勿任意加 -v)
   - kiosk-hub_pg_data       PostgreSQL 資料
   - kiosk-hub_app_uploads   上傳檔 (uploads/member 會員人臉照片、uploads/menu 餐點照片)
   - kiosk-hub_app_database  database/ (線上端主要資料在 PostgreSQL，此處只有備用金鑰等小檔)
   - kiosk-hub_caddy_data    HTTPS 憑證

7. 備份
   注意：後台的「整庫備份/還原」只支援 SQLite，線上端請用以下方式。
   (0) 自動備份 (docker-compose.yml 的 backup 服務，預設啟用)：每天 BACKUP_AT (預設 03:30) 以 pg_dump 備份到
       volume kiosk-hub_pg_backups，保留 BACKUP_KEEP_DAYS 天 (預設 14)；在 .env.hub 調整。
         docker compose exec backup ls -l /backups                    查看備份檔
         docker compose exec backup pg_restore_check.sh              還原演練：把最新備份還原到暫存資料庫並比對筆數
         docker compose cp backup:/backups/<檔名> ./                   複製到主機 (請再複製一份到其他主機或雲端)
       上傳檔 (照片) 不在自動備份內，請依 (2) 另外備份。以下 (1)~(4) 為手動方式。
   (1) 資料庫 (pg_dump 自訂格式，可選擇性還原)：
     mkdir -p backups
     docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backups/kiosk-$(date +%F).dump
   (2) 上傳檔：
     docker compose exec -T app tar czf - -C /app uploads > backups/uploads-$(date +%F).tgz
   (3) 排程建議：每天營業結束後 (例如凌晨 3 點) 自動備份，保留 14 天，並複製一份到其他主機或雲端儲存。
     crontab -e 加入 (專案放在 /opt/kiosk 時；crontab 內的 % 必須寫成 \%)：
       17 3 * * * cd /opt/kiosk && docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backups/kiosk-$(date +\%F).dump && docker compose exec -T app tar czf - -C /app uploads > backups/uploads-$(date +\%F).tgz && find backups -type f -mtime +14 -delete
   (4) 還原 (會覆蓋現有資料，請先停止 app)：
     docker compose stop app
     docker compose exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists' < backups/kiosk-2026-10-22.dump
     docker compose exec -T app tar xzf - -C /app < backups/uploads-2026-10-22.tgz   (app 停止時改用 docker compose run --rm -T app tar xzf - -C /app)
     docker compose start app
   建議每季實際演練一次還原 (可在另一台主機上做)，確認備份檔可用。

8. 更新版本
     (1) 先備份 (上一節的 (1)(2))
     (2) docker tag kiosk-hub-app:latest kiosk-hub-app:previous      (保留舊版映像檔以便回復)
     (3) 取得新版程式 (git pull 或覆蓋檔案)
     (4) docker compose up -d --build
         app 重啟時會自動執行資料庫遷移；期間約數秒無法連線，
         各頁面的即時連線 (SSE) 會自動重連。
     (5) docker compose ps 確認 healthy、docker compose logs app 確認沒有錯誤。
   回復舊版：新版若已遷移資料庫結構，需先還原更新前的 pg_dump，再
     docker tag kiosk-hub-app:previous kiosk-hub-app:latest && docker compose up -d --no-build app
   清理舊映像檔：docker image prune

9. 調整效能 (.env.hub，修改後 docker compose up -d)
   - GUNICORN_WORKERS (預設 2)：worker 行程數，一般 2~4。
   - GUNICORN_THREADS (預設 128)：每個 worker 的執行緒數。每條 SSE 長連線 (廚房、取餐、叫號看板、POS)
     會一直占用一條執行緒，每個 worker 最多 85 條 SSE，請勿低於 100。
   - 每個 worker 最多約 15 條資料庫連線，worker 數 × 15 不可超過 PostgreSQL 的 max_connections (預設 100)。
   - gunicorn 的 timeout 是 worker 心跳逾時，不會中斷 SSE 長連線 (說明見 deploy/gunicorn.conf.py)。
   - 背景排程 (自動行銷、Webhook、每日工作) 每個 worker 都會啟動，但同一時間只有一個「排程主控」執行
     (資料庫租約 30 秒，主控 worker 重啟時由其他 worker 接手)，不會重複發券、推播或送 Webhook。

10. 疑難排解
   - https://網域/ 顯示 502：app 尚未啟動完成或啟動失敗，查看 docker compose logs app。
   - /healthz 回 503：app 連不到 PostgreSQL，查看 docker compose ps postgres 與 DATABASE_URL 密碼。
   - 憑證申請失敗：確認 DNS 已指向本機、80/443 可從外部連入，查看 docker compose logs caddy。
   - 時間不對：docker compose exec app date 應顯示 CST (台灣時間)。
   - 進入容器執行指令：docker compose exec app flask --app run db current

11. 負載測試 (上線前、或調整 GUNICORN_WORKERS / 主機規格時；勿對正式資料庫執行)
   tests/load_gunicorn_pg.py 模擬尖峰時段：點餐機訪客 (瀏覽菜單 → 結帳，部分搶同一個限量餐點)、POS 收銀員、
   廚房出餐、員工 SSE 長連線、外部系統以 API 金鑰 cursor 追蹤訂單；每位虛擬使用者以不同的 X-Forwarded-For 來源 IP
   (不會被每 IP 頻率限制擋下)，結束後列出各端點延遲並檢查一致性。
   a. 準備一個測試用的線上端 (新的 PostgreSQL 資料庫、Redis、TRUSTED_PROXY_COUNT=1、GUNICORN_WORKERS=4)，
      docker compose exec app flask --app run demo seed --days 14 --password LoadTest!2026
   b. 在另一台電腦 (避免與伺服器搶 CPU) 執行：
      python tests/load_gunicorn_pg.py --url https://測試網域 --password LoadTest!2026 \
          --kiosks 20 --cashiers 3 --kitchens 2 --sse 20 --duration 90 --database-url postgresql://...
      (--database-url 可連到測試資料庫時才會做「不遺失 / 不重複 / 不超賣 / 取餐號 / 收款紀錄 / 排程主控」檢查)
   c. 全部顯示 ✔ 才算通過；結束代碼 0 = 通過。
   參考結果 (2026-10-26，2 vCPU / 8 GB 一台機器同時跑 PostgreSQL 16、Redis、gunicorn 4 worker × 128 執行緒與負載產生器)：
   - 一般尖峰 (20 台點餐機 + 3 台 POS + 2 台廚房 + 20 條 SSE，90 秒)：576 張訂單 (6.3 張 / 秒、約 2.3 萬張 / 小時)；
     點餐機結帳 p50 80 ms / p95 345 ms、菜單頁 p50 35 ms / p95 137 ms、POS 結帳 p50 77 ms / p95 209 ms、
     廚房看板 p50 30 ms / p95 64 ms、POS 當日訂單 p50 76 ms / p95 249 ms；每個 worker 記憶體約 230 MB。
   - 壓力 (60 台點餐機 + 6 台 POS + 2 台廚房 + 40 條 SSE，120 秒，CPU 滿載)：1267 張訂單 (10.2 張 / 秒)；
     結帳 p50 1.7 s / p95 5.5 s (CPU 不足排隊)，沒有任何 5xx；每個 worker 記憶體約 330~360 MB (多次測試後持平，無洩漏)。
   - 兩種情境的一致性檢查全部通過：成功回應的訂單都在資料庫且沒有重複建單、限量餐點剛好賣完不超賣、取餐號不重複、
     每張訂單都有收款紀錄、多 worker 只有一個排程主控、每條 SSE 都收到其他 worker 的訂單通知 (Redis)、
     對外 API cursor 沒有漏掉任何訂單。廚房兩台同時按出餐時，後到的回 409 (預期行為，畫面會重新整理)。
   - 依測試結果的調整：order.pickup_at 加索引 (遷移 0023；訂單 40 萬筆時「今天的訂單」查詢 30 ms → 0.2 ms)；
     看板 / POS 收到訂單通知後最多每秒重新抓一次 (尖峰時不會因連續通知而一直不更新，也不會放大伺服器負載)。
   - 容量建議：結帳在同一家店依序取號 (取號到提交為同一筆交易)，單店每秒約 10 張以上需要更多 CPU；
     一般門市 / 多分店線上端 2 vCPU、GUNICORN_WORKERS=2~4 即足夠。當天訂單超過約 3000 張時 POS「當日訂單」一次約 4 MB、0.4 秒，
     如有這種量級請告知 (可改為分頁或只抓異動)。綠界測試環境本次無法連線 (網路政策封鎖)，付款流程以模擬通知測試 (第五節)。


二、本機門市端部署 (Windows)
--------------------------------------------------------------------
1. 安裝
   - 安裝 Python 3.13 (勾選 Add to PATH)，在專案資料夾 (例如 C:\kiosk) 執行：
       python -m venv venv
       venv\Scripts\pip install -r requirements.txt
     (gunicorn 只用於 Linux，Windows 上會自動略過。)
   - 從舊版升級時，OpenCV 已改用 opencv-python-headless，請先移除舊套件再安裝，避免兩個套件互相覆蓋：
       venv\Scripts\pip uninstall -y opencv-python
       venv\Scripts\pip install -r requirements.txt
   - 複製 .env.example 為 .env，至少設定 ADMIN_USERNAME / ADMIN_PASSWORD。
   - Windows 時區必須是「(UTC+08:00) 台北」並開啟自動校時 (營業日、換日結案都依電腦時間)。
   - 先手動執行一次 venv\Scripts\python serve_windows.py，確認 http://127.0.0.1:5000/ 可開啟。

2. 開機自動啟動 (以 Windows 服務執行 Waitress，二擇一)
   (A) NSSM (建議；可在當機時自動重啟並保存 log)：
       下載 nssm (https://nssm.cc/)，以系統管理員身分開啟命令提示字元：
         nssm install KioskPOS C:\kiosk\venv\Scripts\python.exe C:\kiosk\serve_windows.py
         nssm set KioskPOS AppDirectory C:\kiosk
         nssm set KioskPOS AppStdout C:\kiosk\logs\service.log
         nssm set KioskPOS AppStderr C:\kiosk\logs\service.log
         nssm set KioskPOS AppRotateFiles 1
         nssm set KioskPOS AppRotateBytes 10485760
         nssm set KioskPOS Start SERVICE_AUTO_START
         nssm start KioskPOS
       (先建立 C:\kiosk\logs 資料夾。) 查看狀態：nssm status KioskPOS；重啟：nssm restart KioskPOS。
   (B) 工作排程器：建立工作 →「不論使用者登入與否均執行」、「以最高權限執行」；
       觸發程序「啟動時」；動作「啟動程式」C:\kiosk\venv\Scripts\python.exe，
       引數 serve_windows.py，開始位置 C:\kiosk；設定頁勾選「如果工作失敗，重新啟動間隔 1 分鐘」。
   (C) 內附腳本 (最簡單)：以系統管理員身分開啟 PowerShell，在專案資料夾執行
         powershell -ExecutionPolicy Bypass -File deploy\windows\install_autostart.ps1
       會建立開機啟動工作 KioskPOS-Server (執行 deploy\windows\start_store.cmd：先校時再啟動，失敗每分鐘重試，
       記錄檔 database\server.log)，並把 Windows 校時伺服器設為 time.stdtime.gov.tw、每天 05:00 再校時一次。
   - 防火牆只對「私人網路」開放 5000 埠給店內其他平板 / KDS 螢幕使用，不要直接開放到網際網路。
   - 電源選項設定「永不睡眠」，避免營業中伺服器休眠。

3. 定期備份 database/ 與 uploads/
   - 系統內建每日自動備份 (後台「系統設定 → 自動備份」設定時間與保留天數，預設 03:30、保留 14 天)：
     一致性快照壓縮成 database\backups\menu-日期.zip，後台「系統監控」(/admin/system) 可查看、立即備份、下載。
     備份仍在同一台電腦，請另外複製到其他磁碟 / 雲端 (例如把 database\backups 設為雲端同步資料夾)。
     上傳檔 (照片) 不在自動備份內。
   - database/menu.db 使用 WAL 模式，營業中直接複製檔案可能得到不完整的備份。其他方式：
     (1) 後台「整庫備份」(平台管理者)：一次下載資料庫 + 上傳檔的壓縮檔，適合手動備份。
     (2) 排程自動備份：建立 C:\kiosk\backup.bat，內容例如：
           @echo off
           cd /d C:\kiosk
           for /f %%i in ('venv\Scripts\python -c "import datetime;print(datetime.date.today())"') do set D=%%i
           mkdir D:\KioskBackup\%D% 2>nul
           venv\Scripts\python -c "import sqlite3;s=sqlite3.connect('database/menu.db');d=sqlite3.connect(r'D:\KioskBackup\%D%\menu.db');s.backup(d);d.close()"
           copy /y database\.secret_key D:\KioskBackup\%D%\ >nul
           robocopy uploads D:\KioskBackup\%D%\uploads /E /R:1 /W:1 >nul
         再用工作排程器每天打烊後執行一次。(sqlite3 的 backup 在營業中執行也是一致的快照。)
   - 備份請放在另一顆磁碟、USB 或雲端同步資料夾，並定期清除過舊的備份。
   - 還原：停止服務 (nssm stop KioskPOS) → 把備份的 menu.db 放回 database\ (同時刪除 menu.db-wal、menu.db-shm)
     與 uploads\ → 啟動服務；或使用後台的「整庫還原」。

4. Kiosk 瀏覽器全螢幕
   - 點餐機開機後自動以全螢幕開啟點餐頁：在「啟動」資料夾 (Win+R 輸入 shell:startup) 建立捷徑，目標例如：
       "C:\Program Files\Google\Chrome\Application\chrome.exe" --kiosk --kiosk-printing --no-first-run
         --disable-pinch --overscroll-history-navigation=0 --user-data-dir=C:\kiosk\chrome-kiosk
         "http://127.0.0.1:5000/?shop=店家代碼"
     Edge 可用：msedge.exe --kiosk "http://127.0.0.1:5000/?shop=店家代碼" --edge-kiosk-type=fullscreen --no-first-run
     --kiosk-printing 會直接列印到預設印表機 (80mm 熱感應收據機請設為預設印表機)。
     離開全螢幕：Alt+F4。
   - 人臉登入需要相機：瀏覽器只允許 https 或 http://127.0.0.1 使用相機。
     點餐機若不是伺服器本機 (以 http://區網IP:5000 連線)，Chrome 需加上
       --unsafely-treat-insecure-origin-as-secure=http://區網IP:5000
     (必須同時指定 --user-data-dir)，第一次開啟時允許相機權限。
   - 專用點餐機可使用 Windows「指派的存取權」(Kiosk 模式) 鎖定只能使用瀏覽器。
   - 關閉螢幕保護程式與自動睡眠、Windows Update 設定在非營業時間重新開機。
   - 其他螢幕：廚房 KDS http://伺服器IP:5000/kitchen、取餐核銷 /pickup、叫號看板 /counter (公開，可用電視全螢幕顯示)。

5. 桌邊掃碼點餐 (顧客用自己的手機)
   - 顧客手機要連上店內 Wi-Fi，且能開啟門市伺服器：在路由器把伺服器電腦設為固定 IP (DHCP 保留)，
     並允許 Windows 防火牆讓 5000 埠在「私人網路」連入 (第一次啟動 serve_windows.py 時的提示選「允許」)。
   - 後台「桌位 QR」：確認「門市網址」(例如 http://192.168.1.10:5000，預設自動偵測) → 新增桌位 (A1-A10) →
     列印桌卡放在桌上。用自己的手機連店內 Wi-Fi 掃一張實際點一次，確認廚房看板出現該桌的訂單。
   - 顧客點餐後訂單直接送廚房 (標示桌號、未結帳)；用餐後在 POS「桌位結帳」一次結清該桌。
   - 桌卡遺失或被拍照外流：在「桌位 QR」對該桌按「重新產生」並重新列印 (舊的 QR code 立即失效)。
   - 門市網址或 IP 變更後要重新列印全部桌卡。店內 Wi-Fi 建議與收銀、伺服器所在的網路分開 (訪客網路)
     時，需確認訪客網路可以連到伺服器的 5000 埠。


三、同步設定 (門市 ↔ 線上)
--------------------------------------------------------------------
架構與合併規則請看 SYNC.txt。設定步驟：

1. 線上端 (已依「一」部署完成)：以負責人登入後台 →「分店管理」→ 新增分店 (例如「台南店」)。
   畫面會顯示一次權杖 (kn_ 開頭)，請立即複製；遺失時按「重新產生權杖」，舊權杖立即失效。
   (也可在主機上執行：docker compose exec app flask --app run sync create-node --name 台南店)

2. 門市端：在專案資料夾的 .env 加上
     SYNC_ROLE=node
     SYNC_HUB_URL=https://您的網域
     SYNC_NODE_TOKEN=kn_……(上一步的權杖)
   重新啟動 serve_windows.py。伺服器會在背景自動同步：
   - 第一次連線時，本機店家改用線上店家的識別碼，並上傳門市既有的菜單、會員、訂單 (資料多時需要幾分鐘)。
   - 之後本機有變更時立即上傳；線上點餐的新訂單以長輪詢接收，通常 1~2 秒內出現在廚房看板。
   - 斷網時照常營業，後台「同步狀態」頁會顯示最後一次錯誤；恢復連線後自動補齊。
   - 手動同步：後台「同步狀態」→「立即同步」，或在命令列執行 flask --app run sync now / sync status。

3. 一個線上店家可以有多家分店 (每家一台門市伺服器、各自一組權杖)：
   菜單、優惠券、紅利設定、員工帳號、會員與點數在所有分店共用；訂單只送到負責出餐的分店；
   庫存各分店獨立 (線上端只保存各分店回報的庫存快照，用於線上點餐)。

4. 注意事項
   - SYNC_HUB_URL 必須是 https (權杖與會員資料經由此連線傳送)。
   - 門市電腦的系統時間要正確 (開啟 Windows「自動設定時間」)：兩邊同時修改同一筆資料時以修改時間較新者為準。
   - 第一家分店連線前，建議先在線上端或第一家分店建立好菜單，其他分店再連線，避免各自建立同名品項。
     (加料選項、紅利設定、相同手機的會員、相同代碼的優惠券、相同帳號的員工會自動合併，其他品項不會。)
   - 門市不要換用另一個線上店家的權杖；需要換店家時請先備份並重新建立門市資料庫。
   - 分店超過 SYNC_NODE_OFFLINE_AFTER 秒 (預設 120) 沒有連線，線上端會暫停該分店的線上點餐。

[ ] 升級舊版門市：先 pip uninstall -y opencv-python，再 pip install -r requirements.txt

業務 / 法規面
[ ] 線上付款 (見第五節)：目前預設為綠界「測試環境」。正式收款前需向綠界申請正式特店 (需公司/商號資料)，
    設定 ECPAY_STAGE=0 與正式的 ECPAY_MERCHANT_ID / ECPAY_HASH_KEY / ECPAY_HASH_IV，並用小額真卡測試一次。
    綠界公開測試金鑰任何人都能偽造付款通知：未設 ECPAY_ALLOW_TEST_KEYS=1 時系統一律拒絕以測試金鑰收款，
    正式環境請確認 .env.hub / 門市 .env 沒有這個設定
[ ] 公開建立店家：線上端預設開放 /tenant/register (ALLOW_TENANT_REGISTER=1，無審核；不需要時設 0，由平台管理者建店)；
    門市主機預設關閉
[ ] 整庫備份 (系統監控頁的「立即備份 / 下載」與後台「匯出系統完整備份包」) 只有平台管理者 (預設店家負責人) 可用
[ ] POS 動用會員儲值金 / 點數 / 寄杯預設需驗證會員身分 (掃會員動態條碼或會員輸入 PIN，否則店長核准)；
    小店信任櫃檯可在「系統設定 → 會員經營」關閉
[ ] 訂位訂金：門市主機要能從外部以 HTTPS 連線 (綠界回傳 /payment/ecpay/reservation_notify)，門市 .env 設定 PUBLIC_BASE_URL
    與綠界正式特店 ECPAY_MERCHANT_ID / ECPAY_HASH_KEY / ECPAY_HASH_IV、ECPAY_STAGE=0；退款失敗會通知，請到綠界後台處理。
    訂金不退的規則 (幾小時前可退、未到不退) 請在訂位頁或店內公告。
[ ] 自動行銷：依個資法第 20 條，會員表示拒絕行銷後須停止 (紅利商城「接收優惠活動訊息」關閉即不再發券 / 推播)；
    LINE 推播需在 LINE 官方帳號付費方案的訊息則數內。
[ ] API 與 Webhook：API 金鑰只顯示一次，請存在對方系統的密碼管理；不用時立即停用。Webhook 只送 https 且不送內網位址
    (自架內網整合才在 .env 設 WEBHOOK_ALLOW_PRIVATE=1)；接收端請以簽章密鑰驗證 X-Kiosk-Signature。
[ ] 舊資料封存：封存檔在 database/archive，帳簿憑證依法保存 5 年以上，請納入每日備份 (異地)。
[ ] 裝置管理：點餐機 / POS 請用固定的瀏覽器設定檔 (清除 Cookie 會失去註冊，需重新配對)。
[ ] 寄杯 / 多次券：同禮物卡屬預收款 (不設使用期限、須履約保證)；後台「寄杯 / 多次券」顯示未兌換次數與預收金額。
[ ] 桌邊線上結帳 (系統設定 → 桌邊線上結帳)：門市主機要能從外部以 HTTPS 連線 (綠界會回傳付款結果到
    /payment/ecpay/table_notify)，並在門市 .env 設定綠界正式特店 ECPAY_MERCHANT_ID / ECPAY_HASH_KEY / ECPAY_HASH_IV、
    ECPAY_STAGE=0 與 PUBLIC_BASE_URL；付款時訂單已在櫃檯結帳或有異動會標記「需退款」並通知，請到綠界後台退款。
[ ] 禮物卡 / 儲值金：屬預收款，依「商品 (服務) 禮券定型化契約應記載及不得記載事項」不得記載使用期限，
    且須提供履約保證 (金融機構保證、信託、同業連帶保證等)；啟用前請確認並在禮物卡上印出保證機構資訊
[ ] 退款：取消已用信用卡 / Apple Pay 付款的線上訂單時，可在「系統設定 → 付款方式」開啟自動向綠界退刷，
    或在「作廢與退款紀錄」按「綠界退刷」；ATM / 超商代碼付款需向顧客取得帳戶後人工匯款。
    正式特店需在綠界廠商後台確認已開通「信用卡退刷 API」
[ ] 個人資料：後台「隱私權告知」填好營運者名稱與聯絡方式；告知頁內容是一般性範本，正式營運前請法律專業人士檢視
[ ] 定期刪除停止使用的會員：在線上端排程每天執行 docker compose exec app flask --app run privacy purge-inactive --apply
    (先不加 --apply 預覽名單)
[ ] 會員註冊的簡訊驗證：後台「系統設定 → 簡訊驗證碼」選擇簡訊服務並填帳密、勾選「註冊時需簡訊驗證手機」
    (未啟用時任何人都能用別人的號碼註冊)
[ ] 進階功能的外部服務 (見第六節)：電子發票、LINE Pay、LINE、簡訊、外送平台、SMTP 都在後台填寫；
    填完按「測試連線」或執行 flask --app run ops check-integrations，並各實際走一次 (小額真實交易)
[ ] 儲值金屬預收款：啟用前確認履約保證 (信託 / 銀行保證) 與定型化契約揭露義務

建議
[ ] 監控：用 UptimeRobot 等服務每分鐘檢查 https://網域/healthz，異常時通知
[ ] 錯誤通知：docker compose logs 只保留在主機上，可另外接 Sentry 等服務
[ ] 調整 GUNICORN_WORKERS / GUNICORN_THREADS：每個分店的長輪詢與每個開著的看板 (SSE) 都會占用一條執行緒


五、線上付款 (綠界全方位金流)
--------------------------------------------------------------------
線上點餐的流程：會員選取餐分店 → 結帳 → 導到綠界付款頁刷卡 → 綠界通知線上端付款成功 → 訂單才送到分店廚房。
逾時 (PAYMENT_TIMEOUT_MINUTES，預設 15 分鐘) 未付款：線上端先向綠界查詢確認，未付款就自動取消並回補庫存與點數。
線上點餐只開放會員；門市 (含顧客用手機連門市網站) 仍可訪客點餐、到店付款。

1. 測試環境 (預設，免註冊、不會真的扣款)
   - 不需設定任何金鑰，使用綠界公開的測試特店 3002607。
   - 測試卡號 4311-9522-2222-2222，有效期限填未來的月/年，安全碼任意三碼，3D 驗證簡訊碼 1234。
   - 綠界要能連到 https://網域/payment/ecpay/notify 才會通知付款結果 (只接受 80/443 埠的公開網址)：
     部署在有網域的線上主機即可；在自己電腦上練習時，可用 ngrok / Cloudflare Tunnel 把本機開放成 https 網址，
     並在 .env 設定 PUBLIC_BASE_URL=該 https 網址。收不到通知時，訂單會在逾時前向綠界查詢補記。
   - 測試後台：https://vendor-stage.ecpay.com.tw (帳號 stagetest3 / 密碼 test1234) 可查看測試訂單。

2. 正式收款
   - 向綠界申請正式特店，取得 MerchantID、HashKey、HashIV，於 .env.hub 設定：
       ECPAY_STAGE=0
       ECPAY_MERCHANT_ID=…
       ECPAY_HASH_KEY=…
       ECPAY_HASH_IV=…
       PUBLIC_BASE_URL=https://您的網域
   - 不想收線上付款 (改回到店付款)：ONLINE_PAYMENT=0。
   - 取消已付款的訂單：可開啟自動退刷 (系統設定 → 付款方式)，或在後台「作廢與退款紀錄」按「綠界退刷」。
   - 開放 ATM / 超商代碼時，綠界會把取號結果送到 https://網域/payment/ecpay/info (同樣需要 PUBLIC_BASE_URL)；
     訂單保留到繳費期限 (預設 ATM 1 天、超商代碼 120 分鐘，可在付款方式設定) 加 30 分鐘才自動取消。

3. 付款測試腳本 (tests/test_payment_ecpay_script.py，不會動到正式資料庫，一律使用綠界測試特店)
     python tests/test_payment_ecpay_script.py            模擬模式：不需網路，模擬綠界通知走完 30 項付款情境
     python tests/test_payment_ecpay_script.py live       實機模式：開瀏覽器到綠界測試付款頁，用測試卡刷卡，
                                                          腳本確認訂單已付款並可同步給分店 (需網路與 playwright install chromium)
     python tests/test_payment_ecpay_script.py live --public-url https://xxxx.ngrok-free.app
                                                          另外驗證綠界伺服器通知 (需先用 ngrok 等把該網址指到本機 5055 埠)

相關程式：app/services/payment_ecpay.py (檢查碼、付款通知、逾時處理)、app/routes/payment.py。


六、進階功能的外部服務 (後台「系統設定」填寫)
--------------------------------------------------------------------
所有金鑰由店家負責人在後台 /admin/settings 填寫 (只有負責人能修改金鑰；已儲存的金鑰不會再顯示，留空 = 不變)，
存在各店家自己的資料庫 (門市 SQLite / 線上端 PostgreSQL)，不會同步到其他主機。每台主機需分別填寫。
沒有填寫或未勾選啟用的服務自動停用，原本的流程照常運作。每個設定頁有「測試連線」按鈕；也可執行
  flask --app run ops check-integrations        (線上端：docker compose exec app flask --app run ops check-integrations)

1. 電子發票 (綠界 B2C)
   - 測試：勾選「使用綠界測試環境」，特店編號 / HashKey / HashIV 留空即使用綠界公開測試帳號 (2000132)。
     測試後台 https://vendor-stage.ecpay.com.tw 可查看開立的測試發票。
   - 正式：向綠界申請「電子發票加值中心」(需公司統編、向國稅局申請使用電子發票)，取得正式特店編號、HashKey、HashIV，
     取消勾選測試環境。開立失敗 (例如網路中斷) 會留在「待開立」，背景每 5 分鐘重送；資料錯誤 (載具不存在)
     顯示在後台「電子發票」頁，修改載具後按「重送」。
   - 需要 Python 套件 cryptography (已列在 requirements.txt)。
   - 外送平台訂單由平台開立發票，儲值金消費在加值時已開立，這兩種不會重複開立。

2. LINE Pay (門市掃顧客付款碼)
   - 向 LINE Pay 申請「線下支付」商店，取得 Channel ID / Channel Secret Key；測試可先用 Sandbox。
   - POS 選 LINE Pay 結帳時會跳出掃碼視窗，以條碼掃描器掃顧客 App 的付款條碼即扣款；
     扣款失敗訂單自動取消、庫存回補。作廢 / 部分退款會自動退回 LINE Pay (失敗時後台「作廢與退款」可重試)。
   - 門市主機需能連到 api-pay.line.me (HTTPS 443)。

3. 信用卡刷卡機
   - 使用銀行提供的刷卡機刷卡後，在 POS 輸入簽單上的授權碼 / 卡號末四碼記帳 (不需串接)；退款請在刷卡機操作，
     後台「作廢與退款」標記完成。

4. LINE 登入與官方帳號
   - LINE Developers 建立 LINE Login channel，Callback URL 填 https://您的網域/auth/line/callback
     (門市網站在店內網路時通常沒有公開網域，LINE 登入建議只在線上端啟用)。
   - Messaging API channel 的 Channel access token (long-lived) 用於取餐完成通知、生日推播、行銷群發。
     會員需先以 LINE 登入綁定，且要加入官方帳號好友才收得到推播。

5. 簡訊驗證碼：三竹簡訊或 EVERY8D 的帳號密碼；測試時選「只記錄 (不發送)」，驗證碼會顯示在「系統監控」頁。

6. 外送平台 (Uber Eats / foodpanda)
   - 需向平台申請 POS 串接資格 (Uber Eats Marketplace API / Delivery Hero POS 整合)，平台會要求公開的 HTTPS 網址：
       Uber Eats   https://您的網域/webhooks/ubereats             (簽章以 Client Secret 驗證)
       foodpanda   https://您的網域/webhooks/foodpanda/<店家代碼>   (Bearer 權杖)
     Webhook 會在收到訂單的那台主機建立訂單。門市主機通常在店內網路，請用 Cloudflare Tunnel 等把上述路徑開放給平台，
     或先使用 POS「外送單」手動登錄 (不需申請)。
   - 在「菜單進階設定」把平台上的品項代碼填在餐點的「外送 / 條碼代碼」；找不到品項的訂單會被拒單並通知。

7. 寄信 (SMTP)、錯誤通知、定期報表
   - SMTP：Gmail 請開啟兩步驟驗證後建立「應用程式密碼」(smtp.gmail.com、587、STARTTLS)。
   - 監控：可填 Webhook (Discord / Slack / Google Chat)、Email、LINE；系統錯誤、印表機離線、發票開立失敗、
     原料低於安全量、主機時鐘誤差過大時通知 (同一事件 10 分鐘內只通知一次)。

8. 網路熱感印表機
   - 支援 ESC/POS 網路印表機 (TCP 9100，例如 Epson TM-T82III、Xprinter)：在後台「印表機與廚房工作站」新增 IP，
     印表機請設定固定 IP。收據機可在「收銀規則」勾選結帳後自動列印；廚房單依工作站分別出單。
   - 印表機離線時列印工作保留在佇列中重試，三次失敗後在後台顯示並通知，可按「重印」。
