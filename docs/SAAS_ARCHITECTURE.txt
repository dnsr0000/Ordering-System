====================================================================
免費多租戶 SaaS 架構 (第一階段)
====================================================================

本文件定義 SaaS 的技術邊界與實作順序。現階段產品免費使用：不建立訂閱、帳單、付款狀態或金流流程。
一般顧客的訂單付款 (例如 ECPay) 與平台是否向店家收費是兩個不同領域，不可共用訂單付款狀態。


一、目前架構
--------------------------------------------------------------------
- 線上端 (hub) 使用 PostgreSQL 與共用 schema；每個店家的業務資料以 tenant_id 隔離。
- 門市 (node) 使用本機 SQLite，可離線營業；同步時以分店權杖識別分店並將資料送到 hub。
- standalone、hub、node 是部署角色，不是租戶方案或收費等級。
- TenantScoped ORM 查詢會自動加 tenant_id；新增與修改時檢查租戶；無租戶情境 fail-closed。
- 跨租戶平台操作集中使用 tenant_bypass()，只允許平台管理功能及明確的系統工作使用。
- 預設店家的 owner 是平台管理者；可查看店家概況與營收、停用或重新啟用其他租戶，操作寫入稽核紀錄。
- /tenant/register 建立租戶、第一位 owner 與預設資料；線上端依 ALLOW_TENANT_REGISTER 開放公開註冊，並有 IP 頻率限制。
- Tenant 目前以 is_active 布林值表示可用或停用；沒有訂閱、方案、試用期、到期日或帳單資料。
- 線上端使用 Docker、PostgreSQL、Redis 與 Caddy；部署與復原程序見 DEPLOY.txt。


二、免費服務原則
--------------------------------------------------------------------
1. 租戶建立後不需要付款即可使用；不因欠款、試用期或訂閱到期停用店家。
2. 初期不設定未經產品決定的分店、員工或會員數上限；註冊仍受 IP 頻率限制。
3. 保留平台管理者因濫用、安全或營運原因停用租戶的能力，並記錄操作者、時間與原因。
4. 租戶資料不得因停止使用而立即刪除；關閉帳戶、匯出、保留期限與正式刪除流程需另外定義。
5. 未來若開始收費，採獨立的 SaaS billing / entitlement 模組；不得把 ECPay 顧客訂單的 paid / pending 狀態當成店家訂閱狀態。


三、租戶資料與安全不變條件
--------------------------------------------------------------------
- 每一筆屬於店家的資料都必須有 tenant_id；跨店關聯需驗證兩端屬於同一租戶。
- 所有 HTTP 請求先解析租戶；登入員工以帳號所屬租戶為準，不採用查詢參數覆蓋。
- API 金鑰、分店權杖及會員 / 員工工作階段都必須綁定租戶；不能只依可猜測的整數 ID 授權。
- 背景工作、排程與佇列訊息需攜帶明確 tenant_id；跨租戶批次操作需逐租戶執行並可重試。
- 平台管理查詢使用明確、最小化的跨租戶路徑；一般業務查詢不得繞過 tenant filter。
- 新增租戶欄位或資料表時，需一併更新遷移、初始化、同步規則、備份 / 還原與隔離測試。


四、租戶生命週期
--------------------------------------------------------------------
目前流程：公開註冊 (若開啟) → 建立 active 租戶與 owner → 使用線上端；平台可將租戶停用或重新啟用。

免費 SaaS 目標流程：
1. 開通：建立租戶、owner 與預設設定；失敗時整筆回復，不留下半成品。
2. 使用：owner 管理自己的店家與分店；平台操作不混入租戶業務資料。
3. 暫停：平台停用租戶後，登入、店家入口與分店同步一致拒絕；重新啟用後可恢復。
4. 匯出 / 關閉：先提供可稽核的租戶資料匯出與關閉申請，再依公布的保留政策刪除或去識別化。

初期沿用立即開通與平台停用機制，不引入待審核或付費狀態。是否新增 email / 電話驗證、租戶自行關閉、
資料保留天數與免費使用額度，是需產品決策的項目；在決策前不新增強制限制。


五、實作階段與驗收
--------------------------------------------------------------------
階段 A：租戶生命週期與資料權利
- 明確定義停用、關閉、匯出與刪除的權限及狀態轉換；先提供平台端可稽核的流程。
- 驗收：停用租戶無法登入 / 點餐 / 同步；匯出只含指定租戶；跨租戶資料仍不可讀寫。

階段 B：自助開通與濫用防護
- 保持免費立即開通；補上註冊失敗回復、重複請求冪等、平台告警與可追蹤的開通記錄。
- 驗收：同一註冊請求重送不重複建立；併發重複 slug / username 有一致錯誤回應；新租戶預設資料完整。

階段 C：營運可觀測性
- 依租戶呈現同步健康、儲存 / 背景工作錯誤與資源用量；先觀測，不自動封鎖尚未公告的額度。
- 驗收：平台可依租戶定位失敗；租戶無法讀取其他租戶的指標或稽核資料。

階段 D：可選的未來方案
- 若日後決定收費，再定義方案、權益、計費週期、付款供應商、欠款寬限與退款政策。
- 屆時以獨立資料模型與服務實作；本免費階段不預先建立虛構的訂閱或收款紀錄。
